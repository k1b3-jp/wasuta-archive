# AI開発指示書

作成日：2026年11月8日／版：0.1／対応企画：わーすた・タイムミュージアム（仮）

この文書を開発担当AIへの指示として使用する。現段階の成果物は開発指示であり、アプリ本体はまだ実装していない。

## 1. 開発の目的

「01_企画書.md」に沿って、一つの実在する公演を探索できるデジタルミュージアムを実装してください。資料の正本と項目の意味は「02_AIデータ収集指示書.md」および収集担当の `data_dictionary.md` に従ってください。

最初の目標は、スマートフォンとPCで閲覧できる一展示室です。全歴史の完成、会員機能、大規模な管理画面は初期目標に含めません。

## 2. 作業を始めるとき

1. 既存の作業環境・リポジトリ・適用される指示を確認する。
2. 既存の構成があれば再利用する。新規の場合の初期候補は、TypeScriptを使う静的Webアプリとする。依存関係とホスティングの制約を確認して具体的な構成を選び、理由を記録する。
3. 収集データの有無、スキーマの版、承認状態を確認する。
4. 実資料が未承認なら、架空の人物・公演と明記したテスト用データで構造を作る。実在メンバーの架空の発言や実績をサンプルに使わない。
5. 調査用原資料と、公開用データを別の保存場所にする。公開データは明示的な項目選択で生成する。

最小構成は、ファイルベースのデータ読み込み・静的生成を基本とする。初期版にログイン、決済、投稿機能、常時稼働するデータベースを追加しない。新規環境では利用するライブラリの現行の公式資料を確認する。

## 3. 必須画面

### A. 入口／小さな年表

- 展示の趣旨、収録期間、資料の最終確認日を示す。
- 対象公演と、確認できた関連する出来事を表示する。
- 未収録期間を、出来事が存在しなかった期間のように見せない。
- 正式な公式企画と誤認させない表記を置く。

### B. 公演の展示室

- 公演名、開催日、会場、状態、短い編集要約。
- 「開催前」「当日」「終演後」「後年の回想」の区分。
- メンバーごとの資料切替。該当資料がない場合は「この展示では確認できていません」と表示する。
- 関連曲・関連公演への移動。
- 「当時をたどる」と「一覧で見る」の表示切替。

### C. 資料カード／詳細

- 発信者、媒体、発信日、出来事との関係、編集要約を表示する。
- 引用を掲載する場合は引用範囲と発言者を明確にし、要約と見た目を分ける。
- 出典の固定URLと該当箇所への手掛かりを表示する。
- 動画の根拠は該当タイムコードを表示する。
- 現在アクセスできない資料は状態を示す。閲覧不可を内容なしと解釈しない。

### D. 出典・収録範囲

- 展示の根拠資料と、収録範囲・欠落・訂正履歴を確認できる。
- 事実記述ごとに該当出典へたどれる。参考文献の一覧だけで代用しない。
- 問い合わせや訂正受付先は、実在し企画者が指定したもののみ掲載する。

## 4. 表示の重要ルール

### 時間の扱い

出来事の発生日で並べる年表と、発信日で並べる資料を区別する。後年の回想カードは、関連する過去の公演に紐付けても、発信日を過去に変更しない。

「当時をたどる」では、その時点までに公開されたと確認できる資料のみを表示する。日付しか分からない資料は日単位で扱い、時刻の順序を捏造しない。発信日時不明の資料は、そのモードから除外し、一覧では日時不明と表示する。

収集基準日以降の出来事は予定として扱い、実施確認のない公演を開催済みにしない。公演の状態と資料が語る状態が異なる場合も、元資料の日付と当時の内容を保つ。

### 根拠と編集

本文の事実記述には `claim_id` を付け、根拠資料へ導線を設ける。本人の言葉と編集者の説明を混ぜない。未確認の数字や関係は空欄・不明表示にし、モデルの一般知識で補完しない。

公開対象は、承認済みの出来事・主張・資料抜粋・関係だけから構成する。資料全体が承認済みでも、その資料から抽出した全主張が自動で承認されたことにはしない。

### 素材

既定では編集要約と原資料へのリンクを使う。画像・映像・音源は、使用状態と条件を確認できるものだけ表示する。外部埋め込みが不可・削除・読み込み失敗でも展示が読めるようにする。自動再生はしない。

## 5. データ取り込みと公開工程

収集AIのJSONL → 型・参照・編集状態の検査 → 公開可能な項目のみ抽出 → 展示用データ生成 → プレビュー → 企画者確認、の順にする。

- スキーマ違反、ID重複、参照切れはエラーにする。
- `pending` / `rejected`、未解決の矛盾、根拠なしの主張は公開本文に出さない。
- 素材利用状態 `unknown` / `do_not_display` は素材を公開しない。根拠情報の表示可否は別に判定する。
- `link_only` は原文・画像・動画を同梱しない。
- 引用は承認済みの `verbatim_excerpt` だけを使う。全文本文から自動的に長い引用を生成しない。
- 表示テキストだけでなく、画像、検索用データ、JSON、ソースマップにも未公開情報が混入しないようにする。
- 調査用データを静的サイトの公開フォルダへ直接置かない。
- 公開用マニフェストにデータの版、生成日時、収集基準日、承認済み項目数を記録する。

初期版の更新はファイル差し替えと再ビルドでよい。取得機能と閲覧機能は分離し、ページ閲覧のたびにSNSへ収集要求を送らない。

## 6. 見た目と使いやすさ

- 史料を落ち着いて読める余白と文字サイズを優先する。過剰なゲームUIや装飾で資料を隠さない。
- スマートフォンでは縦方向の時系列を基本とし、横スクロールを必須にしない。
- メンバー色を使う場合は色の根拠と時期を確認し、名前など色以外でも判別できるようにする。
- キーボード操作、見えるフォーカス、見出し構造、十分なコントラスト、画像の代替テキストを備える。
- 動きは控えめにし、動きを減らす端末設定に従う。
- 主要情報と出典は、演出を待たずに読めるようにする。
- 公開素材が不足しても成立する、文字と時系列中心のレイアウトを用意する。

## 7. 初期版で作らないもの

実在人物との生成会話、歴史を変える選択肢、人物評価の数値化、恋愛・親密度、収益ランキング、ユーザー投稿、全SNSのリアルタイム連携、全文検索基盤、多言語翻訳、商用分析サービスは初期対象外。必要性が確認された段階で別途設計する。

探索済み状態を実装する場合は端末内保存にし、削除する操作を用意する。利用者の行動を外部へ送る仕組みは初期版に含めない。

## 8. 必須の検証

以下は意味のある境界テストとして自動化し、実画面でも確認する。

| 検証 | 合格条件 |
|---|---|
| 承認と公開 | 未承認の資料・主張・素材が公開成果物に混入しない |
| 時系列 | 後年の回想が当時の発信として表示されない |
| 日付精度 | 日付のみの記録に架空の時刻を追加しない |
| 出典 | 各事実記述から対応する資料・該当箇所に進める |
| 訂正・予定 | 変更・中止・未実施を開催済みと誤表示しない |
| 欠落 | メンバーの資料なし、URL切れ、画像なしで画面が破綻しない |
| データ契約 | 参照切れ、重複ID、不正な列挙値を検出する |
| 表示・操作 | 小画面とPCで読め、キーボードで主要操作ができる |
| 外部コンテンツ | 埋め込み失敗時も出典リンクと概要を読める |
| 入力の扱い | 資料由来HTMLや不正URLを、そのまま実行・表示しない |

ビルド、型検査、関連テストを実行し、実行結果を報告する。画面はスマートフォン幅とPC幅で確認し、スクリーンショットを残す。不要なテストの水増しをせず、史実の誤表示と公開データの漏出を中心に検証する。

## 9. 完了条件と納品

一展示室を開き、公演概要 → 開催前 → 当日 → 終演後 → メンバー視点 → 出典の流れを、補助なしでたどれること。実資料がない区画は欠落と表示し、架空の事実で完成させない。

納品物：実装一式、起動・ビルド手順、データ更新手順、公開項目の仕様、検証結果、画面画像、既知の制約、次の作業一覧。

成果の状態を次のように分けて報告する。

- 画面試作：架空データ等で構造を確認した状態。
- 展示プレビュー：実資料を使用し、編集承認の残件がある状態。
- 公開候補：承認・素材確認・検証を完了した状態。
- 公開済み：実際に公開操作を実施し、公開先を確認した状態。

今回の指示だけで公開・課金契約・外部連絡は行わない。まずレビューできるプレビューを作る。公開の判断が必要になったら、完成したプレビュー、収録範囲、素材の状態、残る制約をまとめて提示する。

## 10. 最初の実行指示

まず環境とデータ契約を確認し、一展示室の画面構成・公開データ生成・検証方法を短く提示してください。その後、許可された作業環境で実装し、プレビューと検証結果まで完成させてください。データ収集の不足で止まる場合も、独立して進められる画面・欠落表示・取り込み検証を進め、不足項目を具体的に記録してください。
