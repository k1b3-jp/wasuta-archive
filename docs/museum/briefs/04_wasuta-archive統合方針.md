# wasuta-archiveへの統合方針

作成日：2026年11月8日／状態：統合提案。リポジトリへの変更・DB適用は未実施。

## 結論

ミュージアムを独立サービスとして新設するのではなく、wasuta-archiveの既存アーカイブに「一公演を深くたどる展示体験」を追加する。

既存の年表を全体の入口とし、イベント詳細から開催前・当日・終演後・後年の回想をたどれるようにする。メンバー、楽曲、衣装、動画は既存データへの関連を利用する。

## 文書の優先関係

この追補は、今回作成した01〜03の「独立した新規アプリ」を前提とする部分より優先する。既存リポジトリの適用される指示、検証済みのデータ構造、公開制御を尊重する。既存設計書に書かれた機能も、実装・動作しているか確認してから再利用する。

| 今回の初案 | 統合時の扱い |
|---|---|
| 新規の静的Webアプリ | 既存Next.jsアプリへ段階的に追加 |
| JSONLを全データの正本とする | JSONLは収集・交換・レビュー待ちの形式。公開データの正本は既存DBと公開ワークフロー |
| 汎用claimsとrelations | 調査中間形式として使用可。DBへ同名の汎用テーブルを新設すると決めず、既存の型別出典・関連へ対応付ける |
| pending / approved / rejected | 調査上の状態。既存draft / review / published / withdrawnとの対応表を作り、approvedから公開へ直結させない |
| ログイン等を作らない | 公開閲覧に新たなログインを求めない。既存の管理・認証機能は再利用 |
| 外部分析を初期版に追加しない | 新規追加しない。既存の設定を調べ、撤去・変更は別判断 |
| 一公演を新しく登録 | 既存イベントIDに紐付ける。重複した公演・楽曲・人物を作らない |

## 新たに加える価値

1. **視点を切り替える資料展示**：同じ公演について、公式・各メンバーの発信を横断する。
2. **発信日と出来事の日付の分離**：当時の発信と後年の回想を明確に区別する。
3. **アカウント台帳と収集範囲**：旧アカウント、改名、取得できない期間まで管理する。
4. **編集された展示の順路**：年表から一公演へ入り、資料と関連曲をたどる。

既存の作品・衣装調査を置き換えず、公式・本人の投稿やブログを追加で接続する。

## 最初の実装単位

まず2015年の調査済み候補を再確認し、開催後の資料と複数メンバーの記録が揃う一公演を選ぶ。既存の年代方針を尊重するが、資料が不足する場合は別年代の候補と比較し、推測で2015年を埋めない。

対象の既存イベント詳細に展示への導線を追加する。展示を詳細内に置くか子ページにするかは、現在の詳細構造を調べて決める。既存URLと一覧機能は維持する。新しいルート名を調査前に固定しない。

実装は、既存IDに紐付く資料カード → 日時と視点の切替 → 出典・欠落表示 → 必要なデータ構造の追加、の縦切りで行う。DB変更は追加型とし、ローカル環境で検証する。本番DBへの適用や公開は別の操作として扱う。

## 受け入れ条件

- 既存イベントURLと一覧・詳細・管理機能が動く。
- 一公演に公式・メンバーの記録が紐付き、日付と出典をたどれる。
- 当時の情報と後年の回想を取り違えない。
- 未承認資料が画面・API・静的成果物から公開されない。
- 既存の公開承認、型別出典、RLSを迂回しない。
- 既存イベントや人物の重複を作らず、再取り込みで件数が不必要に増えない。
- 資料がないメンバーや取得不可の媒体を、存在しなかったと誤表示しない。
- 新規機能の検証と、変更範囲に対応する既存の検証を通す。既存コマンドに自動修正が含まれる場合は変更範囲を確認する。
